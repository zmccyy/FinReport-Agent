## 二、高危修复详情

### H1. select_table：母公司段终止标题缺失 → 全文档尾并入合并段

**文件**：`ai-service/app/modules/extractor/handler.py`（`select_table`）

**修复**（三层防御）：
1. **隐式边界**：段终止标题检测从「仅当前报表的母公司标题」扩展为「全部六类报表标题中除当前合并标题外的任一标题」（`_ALL_TITLES`）。正常文档序中首个命中的仍是母公司标题（语义不变）；母公司标题缺失（换行拆块/措辞变体/段缺失）时，下一张报表的标题成为隐式终止，起始页之后到文档末尾的母公司表/附注表不再并入。
2. **密度收窄兜底**：六类标题均缺失时，顺序扫描关键词命中页（`_page_text` 含表格 HTML），间隔超过 1 页无命中即停止（附注页的「货币资金」讨论不得扩展段尾），段尾容忍 1 页无命中续页。
3. **硬上限**：段长受 `_MAX_SEGMENT_SPAN = 7` 页约束，兜住 prompt 体积（16384 token 预算不再可能被打爆）。
4. 触发兜底时 `LOGGER.warning` 输出收窄区间，根因可见。

**测试**：`test_select_table_implicit_boundary_when_parent_title_missing`（母公司缺失 → 段在「合并利润表」页截断，附注页排除）、`test_select_table_density_fallback_when_no_end_titles`（六类标题均缺 → 远端附注页含关键词也不并入）。

### H2. extract 缓存：读取侧无 success 过滤，存量脏缓存重放 7 天

**文件**：`backend/src/main/java/com/finreport/service/orchestrator/TaskOrchestrator.java`（`checkCacheAndReplayOrDispatch`）

**修复**：`lookupAll` 结果先过滤 `Boolean.TRUE.equals(entry.getValue().get("success"))` 再判 `size() == 3`；被过滤的脏条目 `log.warn`（含 pdfMd5 + step）。修复前写入的 success=false 条目自此视为 miss → 走 MQ 重抽 → 新 success 结果覆盖写同 key（写侧已有门控）→ **自愈，无需部署时手工清 Redis**。

**测试**：`shouldFallThroughToExtractDispatchWhenCacheEntryHasSuccessFalse`——三表全命中但 BS 为脏条目 → 走 MQ、不重放、不写库；既有 `shouldSkipExtractAndReplayWhenAllCached`（全 success 仍重放）回归通过。

### H3. compose JWT 默认密钥绕过 fail-loud 校验

**文件**：`deploy/docker-compose.yml`、`deploy/.env.example`

**修复**：base compose 的 `JWT_SECRET` 默认值（52 字符公开开发密钥）移除，改为 `${JWT_SECRET:-}`——未在 .env 显式配置时 `JwtSecretValidator` 启动即抛「JWT_SECRET 必须至少包含 32 个字符」，**fail-loud 恢复**。开发栈走 base + dev overlay（AGENTS.md §7.1 唯一 sanctioned 路径），dev overlay 保留开发默认值不受影响；单独跑 base compose 属类生产用法，缺密钥拒启是正确行为。`.env.example` 注释同步更新。

**取舍说明**：未把开发默认值加入校验器黑名单——dev overlay 未启用 local profile，黑名单会误伤开发栈。M4.10 曾因「base compose 单独跑 E2E 崩溃」注入默认值，该用法本身偏离 AGENTS.md 规定的启动方式，审查明确判定为静默公开密钥风险，故恢复 fail-loud。

### H4. StatementPageFilter：非锚点文档零表格识别 + 跨文档状态泄漏

**文件**：`ai-service/app/modules/parser/document_parser.py`

**修复**：
1. `StatementPageFilter` 新增 `reset()`（重置 `_last_anchor`）与 `anchor_hit(page_text)`；`DocumentParser.parse_bytes` 每次解析前 reset——单例 parser（parser/handler.py 模块级 `_parser`）的 `_last_anchor` 不再跨文档保留，前一份 143 页文档的锚点不会把后一份文档的早前页误判为候选页（PP-Structure OOM 路径不再回归）。
2. **文档级预扫**：`parse_bytes` 对全页 `get_text("text")` 做一次锚点扫描（PyMuPDF 文本提取为毫秒级，远轻于 PP-Structure）；**任一页命中才启用过滤，否则该文档退回全页识别旧行为**并 `LOGGER.warning`。扫描件/标题变体文档不再「零表格识别且无日志」，相对旧行为（图像级识别）的明确回归被消除。
3. **取舍**：无文本层的大型扫描件退回全页识别后 OOM 风险回归（即旧行为）——相对「零识别 + 根因不可见」是更优失败模式；生产 `enable_ocr=False` 不变。已写入代码注释。

**测试**：`test_statement_page_filter_state_resets_between_documents`（文档 A 锚点页 2 泄漏时会把文档 B 的页 4 误判为候选；reset 后仅页 0）、`test_table_recognition_falls_back_when_document_has_no_anchor`（无锚点文档两页均调用 layout analyzer）。

## 三、中危修复详情

### M1. 文本降级重建：无标题边界 + 附注号粘值 + 块级科目名熔合

**文件**：`ai-service/app/modules/extractor/handler.py`（`_html_from_text_blocks` 及调用点）

**修复**：
1. **标题边界**：签名增加 `min_y0`，起始页传 `start_title_y0`——CF 头部页上方的利润表尾块（「六、综合收益总额85,305,341,965.73」）不再被吞入现金流量表降级页。
2. **附注号粘值**：金额正则改严格千分位分组 `(-?\d{1,3}(?:,\d{3})+\.\d{2})`——「资产处置收益53553,106,625.19」中前导组「53553」不是合法千分位分组，正则从第 2 位起命中真实金额 `553,106,625.19`（约 178 倍虚增消除），残留附注号由名称尾随剥号规则清除。

4. **取舍**：无千分位的小值行（如「500.00」）不再匹配降级重建——错误数据（虚增 178 倍）危害大于缺行，注释说明。

### M4. 重连后 ack 调度到旧 channel：已成功任务被完整重复执行

**文件**：`ai-service/app/mq/consumer.py`

**修复**：
1. **在途去重**：新增 `_in_flight: set[(task_id, step)]` + `Lock`。`on_message` 校验通过后先查在途：命中（= 原投递仍在工作线程处理期间收到重投，正是 7 分钟 parse 遇 broker 闪断的场景）→ 直接 `basic_ack` 丢弃重投件并 warning——**parse 不再重跑、DeepSeek 不再双倍计费**；终态进度由原投递发布，L2 幂等键兜底。`_process` 用 `try/finally` 保证键在成功/失败/进度发布失败三种路径下都释放（L2 重试的新消息不会被误判为重复）。
2. `_schedule_threadsafe` 增加 `channel.is_open` 检查（getattr 容错 duck-typed 测试桩）：旧 channel 随旧连接关闭后，不再把其 ack 操作调度到新连接上再吞异常。
3. **残余竞态**（接受并注释）：原投递已处理完、ack 失败后才到达的重投仍会重复执行一次，窗口极小，由 L2 幂等键兜底；FAILED 路径的 DLQ 意图不受影响（重投件 ack 的前提是原投递在途且终将发布进度）。

**测试**：`test_on_message_acks_duplicate_in_flight_delivery`（原投递入队 → 重投直接 ack 不入队 → 原投递处理完释放键 → 新投递正常入队）。

### M5. 截断 AiException 绕过两层重试链

**文件**：`ai-service/app/modules/extractor/validator.py`（`extract_with_retry`）

**修复**：首次 `extractor.extract(...)` 包 `try/except AiException`——异常（API 截断：content 空 + finish_reason=length，或重试耗尽类瞬时错误）构造失败 `ExtractionResult`，走既有「invalid → build_retry_prompt → 0.1 温度重试」链，恢复旧行为（empty model output）的挽回机会。**重试轮不捕获**：仍抛 AiException 则上抛终态 FAILED → L2 `scheduleRetryOrFail` 走任务级重试——刻意不返回 success=false 假成功（会触发「步骤 SUCCESS 但 StatementWriter 跳过写库 → CHECK 饥饿」的 H2 同款病理）。

**测试**：`test_extract_with_retry_recovers_from_first_attempt_ai_exception`（首抽抛截断 → 重试成功）、`test_extract_with_retry_propagates_retry_attempt_ai_exception`（重试仍抛 → 上抛）。

### M6. 单工作线程 + prefetch=1 + 300s 超时（不改码，已知取舍）

`prefetch_count=1` 为 AGENTS.md §8.1 明文强制约束（「MQ prefetch_count=1 兜底，勿擅自调大」）；单工作线程是 M4.10 心跳饿死修复的设计（拆 I/O 与工作线程）；300s 超时是质量优先于单步 SLA 的有意取舍（config.py 注释已记录 16384 tokens 实测 2-4 分钟/次）。

**缓解路径**（已写入本报告备查）：吞吐瓶颈按 AGENTS.md §15 Q2 扩 ai-service worker 副本（CPU 即可），不动 prefetch。若未来要突破 120s EXTRACT SLA，需在 spec 层提出变更申请（压缩 prompt 或拆分抽取粒度），不在本轮修复范围。

## 七、残余风险与已知取舍

1. **M6 不改码**：prefetch=1 是 AGENTS.md §8.1 硬约束；单次 300s 挂起仍会阻塞该 worker 的后续消息，缓解路径为扩 ai-service 副本。SLA 突破需 spec 变更申请。
2. **H4 扫描件 OOM 取舍**：无文本层的大型扫描件退回全页识别后，M4.10 引入过滤器前存在的 OOM 风险回归（旧行为）；相对「零识别 + 无日志」判定为更优失败模式，注释与报告均已记录。
3. **M4 残余竞态**：原投递处理完成后、ack 失败后才到达的重投仍可能重复执行一次（窗口极小），L2 幂等键兜底数据一致性，成本影响为偶发一次重复 API 计费。
4. **M1 小值行取舍**：降级重建不再匹配无千分位小值（如「500.00」）——宁缺勿错；影响限于 PP-DocLayout 漏检页的兜底路径。
5. **M2 未改门槛语义**：0.9106 门槛仍只覆盖合并+本期；上期/母公司契约回归现有告警可见但不会判 FAIL，四粒度 GT 扩建是彻底解法（后续任务）。
6. **H3 dev overlay 密钥仍为公开开发值**：仅限本地开发栈（base + dev overlay）；生产必须经 .env/密钥管理注入——这是 dev overlay 的设计边界，与 base fail-loud 不冲突。
