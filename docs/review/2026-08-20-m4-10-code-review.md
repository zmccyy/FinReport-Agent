## 一、高危（数据正确性 / 安全，4 项）

### H1. select_table：母公司段终止标题缺失 → 全文档尾部并入合并段
`ai-service/app/modules/extractor/handler.py:321`
- 机制：`end_page` 找不到「母公司XXX表」标题时保持 `None`，else 分支（line 323-325）把起始页之后**到文档末尾的所有表**（母公司表、附注表等）拼进 `merged_html`，且 scope 恒标「合并」。旧版关键词评分不存在此失败模式。
- 触发：标题换行拆块（`母公司现金流量\n表`）、措辞变体、母公司段缺失的报告。茅台仅因三个母公司标题齐全而通过。
- 后果：混合口径数据落库为合并口径；或 5KB→上百KB HTML 打爆 16384 token 预算 → 任务 FAILED，日志只有泛化的「未找到合并标题段」。
- 建议：end_page 缺失时应按关键词密度收窄段尾，而非默认到文档尾。

### H2. extract 缓存修复只堵写不堵读：存量脏缓存继续重放 7 天
`backend/src/main/java/com/finreport/service/orchestrator/TaskOrchestrator.java:765`（修复本体在 829）
- 机制：`storeExtractCache` 只对 success=true 写入；但读取侧 `checkCacheAndReplayOrDispatch → lookupAll → replayCachedExtracts`（line 765-810）无 success 过滤、无失效机制，`ExtractCacheService.TTL = 7 天`（ExtractCacheService.java:43-44）。
- 触发：修复前已写入的 success=false 条目（决策记录承认验收前靠「清 Redis extract 缓存」才通过）。
- 后果：同 PDF 重传 → 三表全命中 → 跳过 MQ → 步骤标 SUCCESS 但 StatementWriter 跳过写库（StatementWriter.java:98-103）→ CHECK 无数据重试耗尽——**与本修复声称消除的 bug 完全相同**。需读取侧过滤或部署时清缓存。

### H3. compose 提交的 JWT 默认密钥静默绕过 fail-loud 校验
`deploy/docker-compose.yml:270`
- 机制：`JwtSecretValidator` 只拒绝 <32 字符或恰等于 `LOCAL_DEVELOPMENT_SECRET` 的密钥；新默认 `finreport-dev-jwt-secret-must-be-at-least-32-characters` 长度合法且字符串不同 → 任何 profile 下校验通过。
- 后果：未覆盖 JWT_SECRET 的部署用公开密钥签发 HS256 token，任何人可伪造任意 userId 的 accessToken，接管全部认证 API。.env.example 的提示性注释代替不了强制校验；该默认值正是为了消除的 WeakKeyException fail-loud 行为。

### H4. StatementPageFilter：非锚点文档零表格识别 + 跨文档状态泄漏
`ai-service/app/modules/parser/document_parser.py:89`（配合 `app/modules/parser/handler.py:58-63` 模块级单例）
- 机制：`is_candidate` 用 `raw.text`（OCR 前文本层）匹配字面锚点 `(合并|母公司)(资产负债表|利润表|现金流量表)`；新过滤器 `_last_anchor=-10000` 时任何页都无法过窗口 → 扫描件/标题变体文档**全页零表格识别**，且无任何日志提示。生产 `enable_ocr=False`，OCR 无法补救。
- 状态泄漏：`DocumentParser` 是模块级单例，`_last_anchor` 跨文档保留——前一份 143 页文档之后，后一份文档的 65-69 页可能被误判为候选页，重新引入该过滤器本要防的 PP-Structure OOM 路径。
- 后果：非 A 股年报格式文档 parse 产物无表 → extract DLQ，根因不可见；扫描件相对旧行为（图像级识别）是明确回归。
